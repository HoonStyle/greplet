# Greplet·Tierwork 마이그레이션 지원 로드맵

상태: 계획 확정, M1 구현 예정. 결정일: 2026-09-05.

## 목표와 결정

제품·고객별 레거시 5세트와 스펙을 대조할 때 구현 차이의 누락과 출처·버전 혼동을 방지한다. 토큰 절감은 이 품질 조건 안에서 평가한다.

- Greplet과 Tierwork 레포는 분리 유지한다.
- 각 제품·고객의 레거시, 현재 코드, 스펙을 별도 워크스페이스로 등록한다.
- 첫 릴리스는 Greplet의 근거 보존·식별·단계적 조회에 집중한다. MCP·CLI 우선이며 비교 UI는 후속이다.
- Greplet은 근거를 반환하고, Serena는 코드 구조를 확인하고, Tierwork는 작업·검증을 조율한다.
- 스펙과 구현 중 채택할 동작은 자동 결정하지 않는다. 고객 수나 검색 점수는 정답의 근거가 아니다.

## 단계와 완료 조건

| 단계 | 결과물 | 완료 조건 |
|---|---|---|
| M0 기준선 | 합성 레거시 5세트·스펙·현재 코드 fixture, 기존 병용 결과와 사용량 | 누락·출처 혼동·오래된 근거를 재현하고 판정 가능 |
| M1 Greplet 기반 | 차이 보존, 버전이 포함된 근거 참조, 짧은 검색과 정확한 본문 조회 | 자동 회귀 검증 + 실제 마이그레이션 파일럿 완료 |
| M2 Serena 연결·비교 | 워크스페이스↔프로젝트 매핑, 심볼 재확인, 기능별 근거 대응 목록 | 다른 프로젝트나 오래된 위치로 연결하지 않음 |
| M3 Tierwork 조율 | 근거·결정·테스트 상태, 중복 검증 합치기, 변경 시 재검증 | 동일 품질 조건에서 전체 비용과 중복 작업 측정 가능 |
| M4 정책 조정 | 작업별 모델·검증 선택 정책 | 별도 평가 과제에서 품질 유지와 비용 개선 확인 |

M4는 충분한 평가 데이터 확보 후에만 진행한다. 그전에는 고정 규칙을 사용한다. 일정은 날짜 대신 완료 조건으로 관리한다.

## 첫 릴리스

[세부 구현·인터페이스·검증 계획](greplet-evidence-v1.md)을 따른다. Greplet에서 근거 규격을 관리하고 Tierwork는 후속 단계에서 이를 소비한다. 이 두 문서는 두 레포에 동일하게 배포하며 구현 상태도 함께 갱신한다.

## 실제 파일럿

기존 마이그레이션 환경에서 고객별 예외, 기본값·상수, 오류 처리, 스펙 불일치, 호출 관계 등 5개 대표 과제를 선정하고 기대 근거를 먼저 고정한다. 현재 Greplet+Serena와 개선 Greplet+Serena를 동일 코드 스냅샷·모델·프롬프트·출력 한도로 과제당 3회 비교한다.

필수 조건은 변형 누락·출처 오인용·오래된 근거 정상 취급이 없고 기존 필수 근거를 놓치지 않는 것이다. 전체 입력·출력·캐시 토큰, 도구 호출 수, 재조회 횟수, 소요 시간을 기록한다. 토큰 절감률은 보고하지만 첫 릴리스의 필수 통과 기준은 아니다.

현재 연결된 환경에는 실제 5세트가 없으므로 합성 검증과 실제 파일럿을 구분한다. 파일럿 전에는 ‘구현·자동 검증 완료’로만 표시하며 첫 릴리스 완료로 표시하지 않는다. 유료 모델 실행은 실제 파일럿을 수행할 때 별도로 실행한다.

## 후속 연결 원칙

- Serena는 출처·버전을 확인한 뒤 실제 심볼을 조회한다. Greplet의 표시용 심볼을 Serena 식별자로 그대로 사용하지 않는다.
- 기능별로 관찰한 차이, 근거, 채택 동작과 결정 이유를 구분한다.
- Tierwork는 근거 참조와 검증 대상 버전으로 작업 상태를 관리한다. 코드·스펙·테스트 조건이 바뀌면 재검증한다.
- 비교 평가 프롬프트는 위임을 강제하지 않는다. 같은 과제의 전체 실행 비용과 품질을 비교한다.
- 학습은 실제 테스트와 사람이 확인한 누락·오탐을 사용한다. 모델의 자체 확신도를 정답으로 사용하지 않는다.
