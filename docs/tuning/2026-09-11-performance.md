# Greplet 튜닝 전후 비교 보고서

> 공개용 익명 표기: 테스트 대상 함수·클래스·프로젝트·질문 ID와 로컬 경로를 대체했다. `Type001.Method001`은 함수 F001을 뜻하며 실제 식별자가 아니다. 평가 수치와 순위는 원본 그대로다. 원본 질문·결과·대응표는 로컬에만 보관하며, 예시 경로는 실제 위치가 아니다.

작성일: 2026-09-11 (Asia/Seoul)

## 결론

전체 10개 워크스페이스 검색의 중복 임베딩을 제거해 중앙값이 **176.5 → 135.3ms**, 약 **23.4% 단축**됐다. 검색 요청당 임베딩 호출은 **10 → 1회**다. 전체 검색 15쌍 모두 결과 ID·점수·순서가 같았다.

기존과 동일한 질문 12개 × 검색 모드 3개 × 5회 평가를 수정 전·후 각각 수행했다. **180쌍 모두 상위 5개 ID·점수·순서가 같았으며**, 정답 함수/페이지 적중은 BM25 **8/12**, 벡터 **11/12**, 하이브리드 **11/12**로 유지됐다. 정확도를 높인 튜닝은 아니며, 확인된 성능 낭비를 줄이면서 검색 결과가 유지되는지 검증한 작업이다.

코드·회귀 테스트·CI 설정은 C:/example/greplet에 반영하고 빌드했다. 비교 측정 당시 운영 서버는 변경하지 않았으며, 실측은 수정 전 운영 모듈과 수정 후 빌드 모듈을 별도 벤치마크 프로세스에서 비교했다. 이후 아래 운영 적용 검증을 완료했다.

## 변경 내용

| 변경 | 수정 전 | 수정 후 | 효과와 범위 |
|---|---|---|---|
| 질의 임베딩 | 워크스페이스마다 같은 질문을 임베딩 | 한 검색 요청 안에서 Promise 공유 | 다중 워크스페이스에서 10→1회, 요청 간 지속 캐시 없음 |
| Ollama 모델 유지 | API에 keep_alive 미지정 | 기본 30m, OLLAMA_KEEP_ALIVE로 조정 | 유지 정책 명시; 최초 로딩을 없애지는 않음 |
| 오류 처리 | 워크스페이스별 재시도 | 공유 호출의 재시도 후 각 워크스페이스 FTS 폴백 | 경고·폴백 결과 유지, 같은 실패 요청 중복 방지 |

FTS-only, 테이블 없음, embeddings:none 경로는 임베딩이 필요한 시점까지 호출을 만들지 않는다. 모델 bge-m3, 청크, BM25, 벡터 거리, RRF 및 후보 수는 변경하지 않았다. 모델 유지 시간 연장은 메모리를 더 오래 점유하는 선택이다. 이번 /api/ps 관측의 모델 VRAM 사용량은 약 664MB(633MiB)였다.

## 동일 테스트 조건

- 질문: 신규 프로젝트 A 코드 4개, 레거시 프로젝트 B 코드 4개, PDF 4개. 레거시 4개는 같은 함수 2개에 대한 자연어/식별자 질문 쌍이다.
- 원문 기반 정답 및 채점 규칙 고정. 기존 평가에서 교정한 PDF 물리 페이지(문서 D004의 4쪽)와 원본 절대경로 매핑을 전후 동일 적용했다.
- 질문 12개 × FTS/vector/hybrid × 5회 = 버전별 180회. 현재 세션에서 수정 전·후 360회 실행했다.
- topN=5, 지정 워크스페이스 한 개, 결과 캐시 우회. 모드 순서를 질문·회차별로 순환하고 예열 3회는 각 통계에서 제외했다.
- 추가 전체 검색: 이전 병목 진단의 질문 3개 × 5회 × 전후 2개 = 30회. topN=6, 워크스페이스 10개, 결과 캐시 우회. 각 쌍의 전후 실행 순서를 번갈아 배치했다.
- 이번 비교의 측정 검색은 총 **390회**다. 이전 180회 자료는 historical.json으로 별도 보존했고 새 측정에 합산하지 않았다.
- 실제 기존 로컬 DB를 조회했다. 재인덱싱·원문 변경·모델 변경 없음. HTTP/MCP/UI 전송 시간 및 동시 사용자 부하는 포함하지 않는다.
- Node v24.14.0, Windows, LanceDB 0.38.0, Apache Arrow 18.1.0. 두 모듈 경로의 DB 구현 해시는 같고 검색 구현 차이는 이번 공유 임베딩 변경이다. scan.js의 기존 제외 경로 처리 차이는 이번 검색 실험에서 실행되지 않는 인덱싱 경로다.

## 정답 검색 품질과 반복 안정성

함수/페이지 Hit@5는 정답 원본 파일의 지정 함수 또는 PDF 물리 페이지가 상위 5개에 있는지 판정한다. 파일 Hit@5는 파일만 맞는 경우도 포함한다. MRR@5는 첫 정답 순위 역수의 평균으로, 상위 5개에 없으면 0이다. 아래 품질 점수는 질문별 첫 회차로 계산하고 반복 5회를 독립 정답 표본으로 세지 않았다.

| 모드 | 파일 Hit@5 전→후 | 함수/페이지 Hit@5 전→후 | MRR@5 전→후 | 5회 순위 안정 질문 전→후 |
|---|---:|---:|---:|---:|
| fts | 9/12 → 9/12 | 8/12 → 8/12 | 0.600 → 0.600 | 12/12 → 12/12 |
| vector | 12/12 → 12/12 | 11/12 → 11/12 | 0.778 → 0.778 | 12/12 → 12/12 |
| hybrid | 11/12 → 11/12 | 11/12 → 11/12 | 0.861 → 0.861 | 12/12 → 12/12 |

전후 180쌍의 상위 5개 ID·점수·순서 일치까지 별도로 단언 검사했다. 두 버전 모두 180회에서 경고 및 결과 캐시 적중은 0이다. 정답 후보는 모두 인덱스 안에 존재한다. 함수 F001의 자연어 질문은 여전히 목표 함수를 놓친다. 이번 수정은 순위 알고리즘을 바꾸지 않으므로 이 품질 한계도 그대로다.

## 모델 유지 시간 검증과 한계

수정 후 /api/embed에 keep_alive: "30m"가 전달되고, /api/ps에 약 30분 뒤 만료가 표시되는 것을 확인했다. 다만 수정 전 관측도 같은 Ollama 세션에서 이미 약 30분을 표시했다. 따라서 **이번 결과만으로 유지 시간이 실제로 5→30분 늘었거나 재로딩 지연이 단축됐다고 주장할 수 없다.**

앞선 최초 검색에서 4,924ms 중 4,748ms가 모델 로딩이었다는 결과는 원인 진단으로 유효하지만, 이번 180회 비교는 예열 후 테스트다. 첫 검색은 여전히 모델 로딩이 필요하다. 유휴 후 재로딩 감소 효과를 수치화하려면 다른 요청이 없는 별도 세션에서 만료 정책을 통제한 장시간 비교가 필요하다.
