# Greplet 잔여 검증 보고서

> 공개용 익명 표기: 테스트 대상 함수·클래스·프로젝트·질문 ID와 로컬 경로를 대체했다. `Type001.Method001`은 함수 F001을 뜻하며 실제 식별자가 아니다. 평가 수치와 순위는 원본 그대로다. 원본 질문·결과·대응표는 로컬에만 보관하며, 예시 경로는 실제 위치가 아니다.

검증일: 2026-09-11. 대상: T01·T02 튜닝이 반영된 실행 모듈.

후속 구현·4개 구성 비교·운영 반영 결과는 [검색 품질 개선안 비교](2026-09-11-search-quality.md)에 기록했다. 아래 내용은 개선 전 진단 시점의 결과다.

## 결론

성능 쪽에서는 **5분 유휴 후 재로딩을 피하는 효과를 통제된 별도 서버에서 확인**했다. 5분 기본 유지 서버는 다음 호출에 2470.5ms, 30분 유지 서버는 27.7ms가 걸렸다. 단, 유휴 구간 비교는 한 번이며, 최초 로딩이나 30분을 넘긴 유휴 후 로딩은 없어지지 않는다.

품질 쪽에서는 **추가 개선이 필요하다.** 검증·복구 함수의 자연어 질문 12개에서 정답 함수 상위 5개 적중은 BM25 1/12, 벡터 6/12, 하이브리드 3/12였다. 이전 혼합 질문의 11/12 결과만으로 하이브리드가 충분하다고 일반화할 수 없다. 이 집합은 실패 유형을 의도적으로 확대한 진단 표본이므로 전체 사용 정확도가 이 비율이라는 뜻도 아니다.

## 모델 유지 시간: 실제 유휴 실험

운영 Ollama(11434)는 그대로 두고 임시 서버 11435·11436을 실행했다. 같은 실행 파일·bge-m3 파일·GPU를 사용했으며, 두 서버 모두 시작 시 모델이 로딩되지 않은 상태임을 /api/ps로 확인했다. 서버 환경의 기본 유지 시간을 5m으로 통제하고 한쪽만 요청에 keep_alive=30m을 지정했다. 모델 추가 다운로드와 인덱스 변경은 하지 않았다.

첫 호출과 예열 3회 후 두 임시 서버에 5분 15초 이상 임베딩 요청을 보내지 않았다. 임시 서버의 만료 시각은 각각 5분/30분으로 표시됐다. 그동안 품질 테스트는 운영 포트에서 수행했으므로 임시 서버의 유휴 타이머를 갱신하지 않았다. GPU는 공유되므로 완전히 분리된 하드웨어 실험은 아니다.

| 조건 | 최초 호출 ms | 실제 유휴 초 | 재호출 직전 로딩된 모델 수 | 유휴 후 호출 ms | 그중 모델 로딩 ms |
|---|---:|---:|---:|---:|---:|
| 기본 5m | 2525.0 | 327.2 | 0 | 2470.5 | 2419.3 |
| 명시 30m | 2578.4 | 327.1 | 1 | 27.7 | 1.5 |

두 조건의 최초·예열·유휴 후 임베딩 벡터 SHA-256은 전부 동일했다. 30m 설정은 모델의 의미 표현을 바꾸는 변경이 아니다. 모델 한 개가 관측상 약 664MB VRAM을 점유하므로 더 오래 메모리에 두는 비용이 있다. 공식 설정 설명: [Ollama FAQ](https://docs.ollama.com/faq).

5m 서버는 실제로 모델이 내려간 뒤 다시 로딩됐고, 30m 서버는 모델을 유지했다. 이번 실험은 설정 전달만 확인했던 이전 검증의 공백을 보완한다. 운영에서 다른 요청·GPU 메모리 압박·다른 모델 사용이 있으면 결과는 달라질 수 있다. 30분 전체 유지·만료 및 동시 부하 지속 시험은 이번 범위가 아니다.

## 실패 유형 확대 평가

원본 소스만 읽어 다음 함수 4개를 정답으로 고정했다.

- Type001.Method001: 입력 데이터 검증
- Type002.Method002: 구성별 입력 검증
- Type003.Method003: 두 상태 집합 비교
- Type004.Method004: 설정 데이터 검증

각 함수에 대한 자연어 표현 3개씩 12개, 정확한 클래스·함수명 질의 4개, 기존 실패 질문 1개를 합쳐 17개다. 질문을 고정한 뒤 3모드 × 5회 = **255회** 실행했다. topN=5, workspace-A 워크스페이스, 결과 캐시 우회, 예열 제외, 검색 모드 순환 조건은 이전 테스트와 같다. 정답 파일뿐 아니라 목표 함수 청크 적중을 엄격히 채점했다. 모든 목표 함수가 인덱스에 존재함을 사전 확인했다.

| 질문 유형 | 질문 수 | BM25 정답 함수 Hit@5 | vector | hybrid |
|---|---:|---:|---:|---:|
| natural_ko | 12 | 1 | 6 | 3 |
| identifier_control | 4 | 2 | 2 | 2 |
| original_failure | 1 | 0 | 0 | 0 |

각 모드에서 17개 질문 모두 5회 동안 상위 5개 ID·순서가 동일했다. 경고와 결과 캐시 적중은 0이다. 반복 횟수를 독립 정답 표본으로 세지 않았다. 같은 함수 4개의 표현 변형들이므로 독립적인 17개 업무 영역을 대표하지 않는다. 클래스 청크나 호출부가 유용하더라도 지정한 함수 구현을 반환하지 않으면 목표 적중으로 세지 않는다.

## 후보 순위로 확인한 실패

목표 함수 F001은 인덱스에 있으며 약 3,695자의 단일 method 청크다. 동일 질문의 벡터/FTS 상위 200개와 기존 hybrid 후보 풀 50개의 목표 순위를 확인했다. 0은 해당 후보 범위 내 없음이다. hybrid 후보 수나 알고리즘은 변경하지 않았다.

| 질문 | FTS 상위 200 내 순위 | vector 상위 200 내 순위 | hybrid 기존 풀 50 내 순위 |
|---|---:|---:|---:|
| Q001-A | 20 | 1 | 2 |
| Q001-B | 0 | 5 | 13 |
| Q001-C | 0 | 16 | 33 |
| Q001-ID | 49 | 8 | 14 |
| Q001-ORIGINAL | 0 | 6 | 14 |

원래 실패 질문의 정답은 vector 6위에서 hybrid 14위가 됐다. 다른 표현에서는 vector 5위가 hybrid 13위로 밀렸다. 따라서 이 표본에서는 융합이 목표 함수 순위를 낮추는 사례가 실제로 있다. 정확한 식별자 Type001.Method001도 FTS 49위, vector 8위, hybrid 14위로, 단순한 식별자 입력이 정의 우선 검색을 보장하지 않는다.

## 청크 문맥 확인

원문 Source001.cs 13–19행의 한국어 클래스 설명은 함수 F001의 목적과 입력 제약을 설명한다. 그러나 이 설명은 Type001 type 청크에만 있고, Method001 method 청크에는 없다.

Extractor/CSharpChunker.cs 53–56행은 파일·네임스페이스·타입명 헤더만 만든다. 69–78행은 클래스 설명을 별도 타입 청크로 만들고, 101–118행 및 179–229행은 메서드 원문에 위 헤더만 붙인다. Method001 자체에는 XML 설명이 없어 method 청크가 22–80행의 구현 위주로 남는다. 소스 규칙과 실제 저장된 청크 양쪽에서 이 분리를 확인했다.

**확인 사실:** 한국어 설명이 목표 method 청크에서 빠져 있다. **원인 가설:** 이 문맥 분리와 영어 식별자 위주의 본문이 자연어 질문의 목표 함수 순위를 낮춘다. 설명 전달을 바꾼 A/B 인덱스 실험까지 한 것은 아니므로 문맥 누락이 유일한 원인이라고 단정하지 않는다.

## 다음 개선 범위

1. 클래스의 간결한 설명을 자식 메서드에 전달하는 청크 구성을 별도 인덱스에서 비교한다. 타입 설명 자체와 구현을 함께 찾는 방식도 비교 대상이다.
2. 자연어 질문에서 벡터 후보가 FTS 융합으로 밀리는 문제를 검증한다. 질의 유형별 융합 가중치/순위 조정은 별도 검증군에서 효과와 회귀를 측정해야 한다.
3. 정확한 클래스·메서드명 질의는 symbol 필드의 정의 우선 후보를 검토한다. 호출부·테스트가 구현보다 먼저 나오는 문제를 분리해서 다룬다.

이번 요청에서는 검증과 원인 진단만 수행했으며 검색 순위·청크·운영 인덱스를 추가 변경하지 않았다. 임베더 재학습을 먼저 할 근거는 여전히 부족하지만, 검색 품질 개선이 필요하다는 근거는 확보됐다.
