# T13 실험안 — 검색 정확도 개선을 위한 고정 후보 재정렬

**실행 상태 갱신 — 2026-09-14:** 준비·개발 측정으로 기존 100문항과 회귀 40문항을 모두 실행했다. 기존 정답셋 기준 전체 적중은 **17/80→32/80**이지만, 회귀군의 기존 적중 손실 3건이 원문 검토에서도 남아 이번 설정의 채택과 새 독립 시험 진입을 보류했다. **새 100문항 목표는 유지하며 확보·실행은 0개**다. 전체 후보 판정과 새 시험·운영 검증까지 완료한 것은 아니다. [실제 설정·전후 결과·실행 범위](2026-09-14-reranker.md)에서 확인한다.

**아래는 실행 전 계획을 보존한 기록이다.** 작성 당시에는 구현·모델 설치·추론·검색 실험 미실행이었다. 작성일은 2026-09-14이며 기준 저장소는 `d141443`, 운영 버전은 `0.11.2`다. 아래 문항 수는 확보 목표이고 채택 기준은 이번 실험을 위한 제안이다. 실행 전에 실제 데이터·모델 revision·환경·설정을 동결 기록으로 남긴다.

**목표는 검색 정확도 개선이다.** 같은 질문에서 정답 근거가 최종 5개 안에 더 잘 들어오는지, 기존에 찾던 정답을 잃지는 않는지 먼저 판단한다. reranker는 이를 위한 첫 가설이며 효과는 아직 확인되지 않았다. 지연·비용은 정확도 개선이 확인된 뒤 운영 적용 가능성을 판단하는 보조 조건이다.

## 1. 이 실험을 먼저 하는 근거

[T12 전체 검색 A0](2026-09-11-workspace-routing.md)는 답이 있는 80문항에서 적중@5 **17/80**이었다. 라벨된 필수 근거군 100개 중 실패 단계는 아래와 같다. **문항 수가 아닌 근거군 수**이며 한 질문에 필수 근거가 여러 개일 수 있다.

| 관측된 실패 | 근거군 수 | 이번 실험에서 구분할 것 |
|---|---:|---|
| 수집한 검색 후보에서 미관측 | 25 | 재정렬만으로 해당 근거를 새로 가져올 수 없음. 인덱스 부재인지 검색 미포착인지는 추가 확인 필요 |
| 융합·범위별 반환 한도에서 탈락 | 4 | 후보 풀 확대 효과와 순위 개선 효과를 분리 |
| 최종 top5 밖으로 밀림 | 54 | 고정 후보 재정렬의 우선 진단 대상. 단일 범위 안에서 6위 이하인 경우도 포함 |

이 집계는 기존 라벨과 trace에서 관측한 범위다. 미판정 대체 근거까지 포함한 전체 정답 수나 reranker의 예상 회복량으로 해석하지 않는다.

Greplet에는 이미 C# 함수·클래스 구조를 보존하는 청킹과 긴 멤버 추가 분할, BM25/FTS, 가중 RRF, 수동 workspace/file 필터가 있다. 현재 `rerank.ts`는 순위를 결합하며 질문과 청크 본문을 함께 읽는 모델은 없다. 이번에는 **검색 입력·인덱스·범위를 고정하고 마지막 순위 변경의 효과**를 확인한다. 구현 근거: [검색 경로](../../indexer/src/search.ts), [현재 융합](../../indexer/src/rerank.ts), [C# 청킹](../../Extractor/CSharpChunker.cs).

## 2. 후보 풀과 비교군

후보 ID는 워크스페이스와 청크 ID의 조합으로 식별한다. 본문이 같아도 서로 다른 범위의 근거를 임의로 합치지 않는다.

**실행 시 보완 — 2026-09-14:** 준비 단계에서 위 조합의 충돌 3건을 발견했다. 실제 고정 후보 키는 `워크스페이스 + 정규화된 절대 파일 경로 + 청크 ID + 시작 줄 + 끝 줄`을 사용했으며 내보낸 후보의 키 충돌·모호한 정답 대응은 0건이었다. 본문 해시도 별도 확인했다. 이 식별 키와 원문 경로는 비공개 자료에만 보존하며 검색 순위나 운영 인덱스를 변경하지 않았다.

- **U — 원래 검색의 후보 합집합:** 같은 요청에서 관측한 vector·FTS 후보를 기존 중복 제거 규칙에 맞춰 합친 집합. 검색 깊이를 늘려 다시 가져온 결과가 아니다.
- **C — 현재 반환 후보:** 범위별 융합·반환 제한·파일 필터를 거쳐 최종 top5 선택 직전에 남은 집합. 주 비교는 C를 그대로 사용한다. 현재 정상 hybrid 경로는 `topN=5`일 때 범위별 반환 한도가 50이므로 10범위에서는 최대 500개 수준이다. 실제 개수와 폴백·정의 조회 경로는 요청마다 기록한다.

| ID | 후보 | 정렬 방법 | 용도 |
|---|---|---|---|
| B0 | C | 현재 운영 순위·입력 순서 그대로 | 개선 전 기준선 |
| BC | C | 현재 점수를 유지하고 동점만 고정 ID 순서로 정렬 | 최종 병합의 동점 정렬 효과를 확인하는 대조군 |
| R1 | C | 질문·본문의 cross-encoder 점수 내림차순, 동점은 BC와 같은 ID 순서 | **주 실험: 후보를 늘리지 않은 순위 개선** |
| U0 | U | 현재 융합 정책을 재현하되 범위별 반환 한도 적용 전 후보까지 병합 | 개발 진단: B0 대비 풀 제한 해제 효과 |
| U1 | U | R1과 같은 모델·입력·동점 규칙 | 개발 진단: U0 대비 순위 효과, R1 대비 풀 확대 효과 |

U0·U1은 개발 단계 진단이며 새 시험의 주 비교군을 늘리지 않는다. 원래 vector/FTS 순위와 융합을 재현할 정보가 부족하면 먼저 관측을 보강하고, 재현되지 않은 U0 수치를 기준선으로 쓰지 않는다. 개발 결과에 따라 U를 쓰는 구현을 채택 후보로 바꾸려면 **새 시험을 열기 전에 별도 계획을 동결**한다.

주 비교는 **R1−B0**이고 **R1−BC**도 함께 보고한다. BC 자체의 효과를 모델 개선으로 합산하지 않는다. R1은 C의 전체 후보를 재정렬하며, 단일 범위에서도 기존 벡터 상위 3개의 최종 순위를 바꿀 수 있다. 따라서 벡터 보호 정책은 B0·BC의 기준선으로 유지하고 지정 범위 회귀를 별도로 검사한다. 정확한 `Type.Member` 정의 우선 조회에 성공한 요청은 모든 방법에서 기존 결과를 그대로 반환하며 재정렬을 우회한다.

BC는 이미 고정한 C의 최종 동점만 점검한다. 후보 생성·중복 제거·범위별 융합에서 먼저 발생한 순서 의존성까지 통제했다고 주장하지 않는다. 개발 단계에서는 C의 나열 순서를 정순·역순·고정 seed 순열로 바꿔 BC와 R1의 결과가 동일한지 확인한다. B0는 원래 입력 순서의 결과로 유지한다.

비용 때문에 C를 50개나 100개로 줄이는 변경은 주 실험에 섞지 않는다. 필요하면 개발 단계의 별도 후보 축소 비교로 기록하고, 잘라내기 전후 필수 근거 보존과 동일하게 축소한 기준선까지 함께 비교한다. 운영 요청 범위·순서는 세 방법에 동일하게 주며 정답 범위 AO나 자동 선택기를 사용하지 않는다.

## 3. 모델·입력·환경 동결

cross-encoder는 질문과 후보를 한 쌍으로 읽어 점수를 계산한다. 검색 후 후보를 재정렬하는 구조는 [Sentence Transformers 공식 설명](https://sbert.net/examples/cross_encoder/applications/README.html)을 참고한다. RRF 점수 결합과 별개의 단계이며 후보별 추론 비용이 발생한다.

첫 후보는 다국어 모델로 공개된 [BAAI/bge-reranker-v2-m3 모델 카드](https://huggingface.co/BAAI/bge-reranker-v2-m3)를 근거로 선정한다. 이는 한국어 코드·문서 검색에서의 우수성을 확인했다는 뜻이 아니다. 임베더 `bge-m3`는 그대로 두고 별도 재정렬 모델을 평가한다.

| 동결 대상 | 최초 설정·기록 원칙 |
|---|---|
| 모델 | 모델 revision 및 파일 해시, tokenizer·라이브러리 버전. 떠 있는 `main` 참조로 재현하지 않음 |
| 입력 | 원문 질문과 `상대 파일 경로 + 심볼 + 청크 본문` 쌍. 정답·평가 라벨·모델이 생성한 답변은 입력에서 제외 |
| 길이 | 최초 쌍 입력 길이 512토큰, 질문을 유지하고 문서 오른쪽을 절단. 이는 실험 설정이며 모델의 최대 지원 길이라는 주장이 아님 |
| 절단 관측 | 원래/입력 토큰 수, 절단 위치, 결정적 근거가 입력 안에 남는지 기록. 질문 자체가 한도를 넘으면 오류·기준선 폴백으로 기록 |
| 점수 | 모델 원점수로 정렬. RRF 점수와 더하거나 범위별 정규화하지 않음. sigmoid 값도 검증된 정답 확률로 취급하지 않음 |
| 실행 | 로컬 평가 모드, 장치·정밀도·배치 크기·seed·결정성 설정 기록. 장치 적합성 예비 검사 후 고정하고 시험 도중 변경하지 않음 |
| 검색 | 기준 커밋, 인덱스·설정 해시, embedding 모델, 질의·필터·범위 순서, U/C의 ID·원순위·본문 해시 및 관측 코드 해시 |

새 모델·입력 길이·점수 혼합을 계속 시도하는 격자 탐색은 하지 않는다. 예비 검사에서 실행 불가나 심한 절단 문제가 확인되면 이유와 수정안을 기록하고 개발 단계에서만 변경한다. 새 시험 결과를 보고 바꾸면 다음 실험으로 분리한다.

## 4. 데이터와 정답 라벨

| 묶음 | 수 | 역할 |
|---|---:|---|
| 예비 검사 | 기존 T12에서 유형별 20개 | 입력 연결·메모리·지연·절단 확인. 아래 개발 100개의 부분집합 |
| 개발·진단 | 기존 T12 100개 | B0/BC/R1 비교, U0/U1 실패 진단. 이미 결과를 본 자료이므로 독립 시험이라고 부르지 않음 |
| 기존 회귀군 | 기존 혼합 40개 | 지정 범위·식별자 동작, 벡터 보호 해제에 따른 손실 확인. 중복 관계를 기록하고 신규 N에 합산하지 않음 |
| **새 봉인 시험** | **100개** | 설정 동결 후 전부 실행. 현재 미확보이며 결과도 없음 |

새 시험은 **단일 범위 근거 60 + 두 범위의 필수 근거가 필요한 질문 20 + 모호한 질문 10 + 범위 밖 10 = 100개**로 구성한다. 주 검색 조건은 전체 범위다. 답이 있는 80개는 자연어 질문으로 작성하며 코드 40·문서 30·코드와 문서 교차 10개를 목표로 한다. 식별자가 섞인 자연어는 포함하되 정확한 정의 조회 회귀는 기존 회귀군에서 별도로 본다. 단일 범위 질문은 10개 범위에 6개씩 배분한다.

같은 근거 대상·질문 바꿔쓰기·밀접한 작업 세션을 묶어 개발/시험 중 한쪽에만 배치한다. 파일의 밀접한 관련 구간도 누출 여부를 검토한다. 질문은 실제 기록 또는 소스를 근거로 작성하고 출처 비율을 공개한다. 모든 모델이 실패하는 질문만 골라 새 시험을 구성하지 않는다. 부족하면 확보 미완료로 남기며, **100개 목표를 줄이거나 기존 질문을 새 질문으로 다시 세지 않는다.**

qrels는 질문별 필수 근거군과 허용 가능한 대체 근거를 기록한다. 여러 범위의 필수 근거와 어느 하나만 있어도 되는 대체 근거를 구별하고, 관련성은 직접 근거 2·보조 1·무관 0·미판정으로 구분한다. 적중 판정에는 해당 필수 근거군을 충족하는 직접 근거만 사용한다.

라벨은 다음 순서로 보강한다.

1. 모델 실행 전 소스에 근거한 질문·필수 근거·분할을 고정한다. 범위 밖 라벨도 고정 스냅샷을 기준으로 확인한다.
2. 모델·정책을 동결하고 모든 비교군을 실행한 뒤, 방법별 상위 20개와 기존 정답을 합쳐 중복을 제거한다. 개발 진단에서는 U0/U1도 같은 깊이로 포함한다.
3. 방법 이름·원래 순위·점수를 숨기고 섞은 후보를 원문 근거로 판정한다. 두 번째 검토자는 신규 정답·불일치·적중 손실 사례를 우선 확인한다. 판정자와 검토 방식, 모델 판정을 썼다면 모델·프롬프트·사람 검토 여부를 남긴다.
4. 최종 top5의 미판정을 해소한 후 같은 qrels로 모든 방법을 채점한다. 미판정을 자동 음성으로 바꾸지 않는다. 해소되지 않으면 판정 보류 건수와 가능한 점수 범위를 보고하고 채택을 보류한다.

라벨 보강에서는 동결한 필수 근거군을 충족하는 후보·대체 근거의 대응을 추가할 수 있다. 결과를 본 뒤 질문 의도나 필요한 근거군 자체를 유리하게 바꾸지 않는다. 라벨 보강은 모델 선택이나 입력 수정에 사용하지 않는다. qrels가 수정되면 버전과 이유를 남기고 모든 방법을 다시 채점한다. 풀 밖 정답을 모두 판정한 것은 아니므로 후보 근거 회수율은 **알려진 필수 근거 기준**으로 표시한다. 새 시험을 실행한 뒤 라벨 오류가 발견되어도 문항을 조용히 빼지 않고 원래 배정과 수정 분모를 함께 남긴다.

## 5. 지표·실패 단계·반복

| 항목 | 보고할 값 |
|---|---|
| 주 품질 | 답이 있는 80문항의 적중@5, R1−B0·R1−BC 차이, 신규 적중·적중 손실 ID |
| 순위·복수 근거 | MRR@5, 복수 20문항의 모든 필수 근거 완성@5. nDCG@5는 graded qrels 판정 범위가 충분할 때 보조로 보고 |
| 후보 보존 | 알려진 근거군의 U→C→모델 입력→top5 생존율. C에 정답이 있는 문항의 조건부 적중은 전체 80개 지표와 구분 |
| 세부 유형 | 코드/문서/교차, 단일/복수 근거, 지정 범위 회귀군. 모호·범위 밖 20개는 80개 적중 분모에 넣지 않고 부적절한 결과 노출·오류를 별도 보고 |
| 실패 원인 | 인덱스 부재 확인 / 후보 미관측 / 융합·반환 한도 탈락 / 입력 절단 / 최종 순위 탈락 / 오류·폴백. 인덱스 확인 전에는 후보 미관측만으로 수집 실패라고 단정하지 않음 |
| 불확실성 | 질문군을 묶은 paired bootstrap 95% 구간, 개선·악화 쌍 수. 주 비교는 R1−B0 하나로 고정하고 나머지는 보조·진단으로 표시 |
| 비용 | 실제 후보 수·토큰 수·모델 평가 쌍 수, 로딩/토큰화/추론/병합 시간, p50/p95·메모리·오류. 금액을 환산하면 근거와 단위를 명시 |

새 시험은 **100문항 × B0·BC·R1 3방법 × 3회 = 900개 순위 결과**를 기록한다. 같은 후보를 재생하므로 이것을 검색 900회로 부르지 않는다. C/U 수집 횟수, 재정렬 추론 횟수, query-document 쌍 수를 각각 집계한다. R1은 결과 캐시를 끄고 3회 실제 추론하며 B0·BC도 같은 입력으로 3회 재생해 재현성을 확인한다. 오류·폴백도 전체 실행 수와 주 지표에 포함하고 성공한 요청만 골라 채점하지 않는다.

**새 시험의 고유 문항 N은 100이고 답이 있는 질문 분모는 80이다.** 반복은 안정성 확인이지 표본 증가가 아니다. 각 회차 점수와 순위 변동을 공개하고 세 회 중 가장 좋은 회차를 대표값으로 선택하지 않는다. 신뢰구간은 문항별 3회 평균을 먼저 계산한 뒤 관련 질문군 단위로 재표집하며, 300회 관측을 독립 표본으로 취급하지 않는다. 실제 질문군 수도 공개한다. 개발·예비·회귀·후속 부하 실행 수는 위 900개와 분리한다.

고정 후보 재생 시간은 재정렬 비용만 설명한다. 운영 적용 검증에 진입하면 같은 환경에서 후보 생성까지 포함한 전후 요청을 교차 실행하고, 캐시 없는 warm 요청·최초 로딩·임베더와 장치 자원 경쟁을 구분한다. 동시 요청 1부터 확인하고 품질·자원 기준을 통과한 경우에만 4·8로 확대한다. 엔진 내부 측정과 HTTP 지연을 섞지 않는다.

## 6. 진행 순서와 판정

| 단계 | 수행·완료 조건 |
|---|---|
| P0 준비 | 데이터 확보·누출 점검, 관측 재현, 모델 로딩·예비 20개 확인. 실제 환경·입력·후보·판정 규칙과 비용 한도를 기록 |
| P1 개발 | 기존 100개와 회귀군에서 주 비교·풀 진단. 개선 근거와 손실·절단·비용을 확인. 통과 가능성이 없으면 여기서 이유를 기록하고 새 시험은 열지 않음 |
| P2 동결 | 채택 후보 R1 하나, 코드·모델·데이터·qrels 초안·최종 비교군·지연 한도 동결. 새 시험 결과 접근 전 기록 |
| P3 새 시험 | 새 100개를 3회 모두 실행하고 익명 순서로 라벨 보강·전후 비교. 결과가 나빠도 일부만 남기지 않음 |
| P4 적용 검증 | 품질 기준 통과 시 실제 요청 경로·동시 부하·모델 실패 폴백 확인. 운영 반영 여부는 이 결과까지 보고 결정 |

P3의 잠정 통과 기준은 **R1이 B0보다 적중 3개 이상 순증, 기존 적중 손실 0, MRR와 복수 근거 완성 저하 없음**이다. BC에 대해서도 적중·MRR·완성이 낮아지지 않아야 하며, BC만으로 개선이 모두 설명되면 reranker 채택 근거로 삼지 않는다. **품질 기준은 세 회차에서 각각 모두 충족해야 한다.** 기존 회귀군은 적중 손실 0, 정확한 정의 조회 경로의 결과·순위 일치를 요구한다. 이 기준은 동결 이후 결과에 맞춰 완화하지 않는다.

운영 비용 한도의 초안은 **warm 전체 요청 p95가 같은 환경 B0의 2배 이내이면서 1초 이내**다. 이는 기존에 합의된 서비스 SLA나 측정값이 아니다. P0에서 대상 장치·부하별 적용 조건과 함께 확정하고 새 시험 전에 문서로 동결한다. cold 로딩과 최고 메모리는 별도 공개한다. 품질이 좋아도 비용 한도나 오류·폴백 검증을 통과하지 못하면 운영 채택을 보류하고 오프라인 개선으로만 기록한다.

모호·범위 밖 요청에 대한 자동 정답 판정이나 응답 거부 임계값은 이번에 추가하지 않는다. 모델 점수가 높은 결과를 정답이라고 표시하지 않으며 이 20개를 정답 회피 성공률로 포장하지 않는다. 이번 평가의 범위는 검색 근거와 순위이고 최종 LLM 응답의 정확성·전체 에이전트 안전성은 별도 평가다.

## 7. 후보 미포착에 대한 후속안 — 보조 질의

T13에서 후보 미포착이 계속 남으면 **원문 검색 + 보조 질의 1개**를 별도 실험으로 비교한다. 원문 검색은 항상 유지하고 함수명·에러 코드·파일 경로·버전 같은 리터럴은 바꾸지 않는다. 질의 생성 실패나 보호 토큰 변형은 원문만 쓰는 폴백으로 기록한다.

비교는 원문만 같은 총 후보 예산까지 깊게 검색한 대조군과 원문+보조 질의를 함께 둔다. 검색 범위·임베더·인덱스를 고정하고 질의별 출처를 남겨, 단순 후보 수 증가와 질의 다양성 효과를 분리한다. 먼저 U/C의 근거 회수율을 보고, 같은 융합·재정렬 설정에서 top5와 전체 지연을 비교한다. 원문 후보를 합집합에 남겨도 최종 top5 적중은 나빠질 수 있으므로 신규 적중과 손실을 함께 본다.

생성 모델·revision·프롬프트·생성 설정·토큰 비용과 시험군은 이 후속 실험 전에 따로 동결한다. T13 새 시험을 보고 설계했다면 그 100개도 개발군으로 전환하고 새 독립 시험을 확보한다. 질의 확장과 RRF를 결합하는 방식 및 주제 이탈 위험은 [RAG-Fusion 원문](https://arxiv.org/abs/2402.03367v2)을 참고하되, 해당 연구의 결과를 Greplet 성능으로 가져오지 않는다.

구조적 청킹은 인덱스/근거 경계 문제, 필터 UX는 실제 범위 지정 문제, 자동 선택기는 필수 범위 보존 문제가 확인될 때 각각 다룬다. [선택기 연구 비교](2026-09-11-workspace-routing-research.md)는 해당 후속 설계의 참고 자료로 유지한다.

## 8. 결과를 남기는 형식

실행 후 별도 T13 결과 보고서와 익명 집계를 추가하고 [튜닝 히스토리](README.md)에 연결한다. 이 계획의 사전 기준은 보존한다. 공개 자료에서는 테스트 함수·클래스·프로젝트·질문·경로를 익명화하고 원문 후보·qrels 대응표·모델 입력은 비공개로 보관한다.

```text
T13 | 문제·가설 | 기준/구현 커밋·모델·설정 해시 | 평가군·고유 N·질문군 수·실제 실행 수
    | 같은 C의 B0/BC/R1 전후 | U0/U1 개발 진단 | 신규 적중·손실·불확실성
    | 실패 단계 이동·절단·미판정 | 지연·메모리·추론량 | 채택/보류·근거
```

계획 수립 당시 확정된 산출물은 **이 실험안뿐**이었다. 이후 준비·개발 측정 결과와 보류 사유는 [T13 결과 보고서](2026-09-14-reranker.md)에 추가했으며, 위 사전 채택 기준은 변경하지 않았다.
